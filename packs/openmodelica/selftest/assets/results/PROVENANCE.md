# Where `ThermalTank.TankRun_res.csv` came from

**It was not written by `omc`.** Read that sentence before you use this file for
anything.

`omc` was not installed on the machine this pack was built on, and that is the
condition the pack is designed around: a tier-2 solver that must degrade honestly
to BLOCKED rather than be faked. Shipping a file produced by a stub that
"pretends to be a compiler" would be precisely the laundering of assumption into
apparent proof that nopekit exists to prevent — worse here than anywhere else,
because the whole argument of this pack is that a number from a run nobody
validated is the silent failure of the domain.

So the file is what it is, stated plainly:

| | |
|---|---|
| **Produced by** | `make_result_csv.py` in this directory — fixed-step classical RK4, 1000 s step |
| **Of** | the single ODE in `../model/ThermalTank.mo`: `C*der(T) = Q - UA*(T - T_amb)` |
| **In the format of** | OpenModelica's `outputFormat="csv"` result file |
| **Regenerate with** | `python3 selftest/assets/results/make_result_csv.py` |
| **Is it a simulator output?** | No. |
| **Is it a real numeric solution?** | Yes — RK4, not a lookup table, not the closed form. |

## Why a synthetic file is the right call here, and what it costs

The tier-0 gates read result *files*. They have no opinion about who wrote one,
and that is the architecture on purpose: a project records a run once on a
machine that has OpenModelica, commits the result, and then gates claims against
it in CI and on every laptop for as long as the model does not change. For that
half of the pack, a file in the right format with real numbers in it is a
complete and honest test fixture.

What it does **not** prove, and what nothing in this directory should ever be
read as proving:

- that `ThermalTank.mo` compiles. Nothing here has compiled it.
- that omc would produce these numbers. It would produce *close* numbers with a
  variable-step stiff solver on its own error-controlled grid, and they would not
  be bit-identical to these.
- that the tier-2 gates work. Those are proven by their own fixtures —
  `../bad/*.mo`, real Modelica that omc genuinely rejects — wherever omc is
  installed. On a machine without it they SKIP, visibly, and their claims resolve
  BLOCKED.

## The format, since this file is also the worked example

```
"time","tank.T","tank.qLoss","der(tank.T)"
0.0,293.15,0.0,0.01
1000.0,302.2133333333333,380.65999999999997,0.008187333333333335
...
25000.0,342.8130761054808,2085.8491964301934,6.7384778903841e-05
```

Quoted header row; `time` first; one column per recorded variable; derivative
columns spelled `der(x)`; dotted names for variables inside a component
(`tank.T` is `T` inside the `tank` component of `TankRun`). A real omc file
additionally repeats a time value at every event — two samples at the same `t`,
one either side of the discontinuity — which is why
`modelica.solution_valid` requires the time column to be non-DEcreasing rather
than strictly increasing. This file has no events, so it has no duplicates; see
`references/result-formats.md` for one that does.

## The mirror

`../mirror/thermal_tank_mirror.csv` is the *closed form* of the same ODE,
generated by `../mirror/mirror_reference.py`. So on this baseline,
`modelica.mirror_agrees` is comparing a numerical integration against an
analytic solution — which is a genuine independent check of the integration, and
is also two Python files rather than a solver against a spreadsheet.

In a real project it is a result file from omc against whatever second
implementation the team ended up writing. The gate does not care; the honesty
requirement is that you say what your mirror IS, in `modelica_mirror_source`, so
the verdict can repeat it.
